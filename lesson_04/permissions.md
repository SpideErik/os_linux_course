# Модель разграничения доступа для Telegram-бота

## 1. Контекст проекта

* **Сервисный пользователь бота:** `tg-bot` (от его имени запускается systemd-сервис бота).
* **Группа разработчиков проекта:** `tg-dev` (в неё входят разработчики: `alex`, `bella`).
* **Корневой каталог проекта:** `/srv/tg-bot`.

## 2. Таблица прав доступа к объектам проекта

## 3. Маска umask для команды

Для участников группы `tg-dev` в профиле оболочки (в `.bashrc` или скрипте окружения) устанавливается маска:
```bash
umask 0027
```

### Расчёт прав для вновь создаваемых объектов:

1. **Для каталогов (базовые `0777`):**
   * Владелец: $7 - 0 = 7$ (`rwx`)
   * Группа: $7 - 2 = 5$ (`r-x`) *(при включенном SGID у родителя группа получит и право на запись, если процесс наследует права каталога проекта)*
   * Остальные: $7 - 7 = 0$ (`---`)
   * **Результирующие права:** **`0750`** (`drwxr-x---`).

2. **Для файлов (базовые `0666`):**
   * Владелец: $6 - 0 = 6$ (`rw-`)
   * Группа: $6 - 2 = 4$ (`r--`)
   * Остальные: $6 - 7 = 0$ (`---`)
   * **Результирующие права:** **`0640`** (`-rw-r-----`).

**Обоснование:** маска `0027` исключает утечку закрытых данных во внешнюю среду сервера (права `others` полностью обнулены), сохраняя при этом удобство совместного чтения файлов членами группы проекта.

## 4. Необходимость Sticky-бита и списков управления доступом (ACL)

### 1. Где нужен Sticky-бит (и почему без него нельзя)
* **Объект:** Каталог `/srv/tg-bot/media` (права `3770`).
* **Почему нельзя обойтись:** В этот каталог одновременно пишут файлы как сам бот (`tg-bot`), сохраняя загруженные пользователями Telegram голосовые сообщения и картинки, так и разработчики (`tg-dev`), тестирующие загрузку медиа. 
  По стандартным правилам UNIX, если у группы есть право на запись в каталог (`w`), **любой разработчик может удалить любой файл**, даже принадлежащий процессу бота. 
  **Sticky-бит** (`1000`) вводит обязательное ограничение: удалить или переименовать файл может только его непосредственный автор (владелец файла) либо суперпользователь `root`.

### 2. Где необходима запись POSIX ACL (и почему без неё нельзя)
* **Объект:** Файл секретов `/srv/tg-bot/.env`.
* **Архитектурная проблема:** В реальном production-окружении разработчики из группы `tg-dev` **не должны знать** боевой токен production-бота (принцип наименьших привилегий). Файлом должен владеть ведущий инженер/DevOps (`lead-dev`), сервис должен запускаться от `tg-bot`, а обычные программисты не должны иметь доступа к файлу:
  * Владелец: `lead-dev` (`rw-`)
  * Группа: `tg-dev` (`---` — запрет чтения токена)
  * Остальные (`others`): `---` (запрет всем)
* **Почему стандартных прав недостаточно:** В стандартной модели POSIX есть только **один** пользователь-владелец и **одна** группа-владелец. Дать доступ сервисному аккаунту `tg-bot`, не открывая файл для всей группы разработчиков `tg-dev` и не открывая его для всех пользователей системы (`others`), невозможно.
* **Решение через ACL:**
  ```bash
  chmod 600 /srv/tg-bot/.env
  chown lead-dev:lead-dev /srv/tg-bot/.env
  setfacl -m u:tg-bot:r /srv/tg-bot/.env
  ```
  Запись ACL точечно наделяет демона `tg-bot` правом на чтение боевых секретов, оставляя команду разработчиков и прочих системных пользователей без доступа к токену.
